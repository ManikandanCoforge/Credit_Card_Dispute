# Limitations

Current state on this branch: 2026-10-25, including missing-evidence routing from COF-38 and the COF-44 scored run. This file describes what the software does now and what it does not do. It does not describe target-state behaviour or claim a capability that is only planned.

The application turns a bank complaint into a cited contract object for a human reviewer. It does that for the supported classifications when the supplied sources allow it, including cases whose evidence is missing. It is not a production dispute system.

| ID | Limitation | Impact | Mitigation and next step |
|---|---|---|---|
| L1 | **Create-only record lifecycle.** The record API supports creation only. There is no update or close operation. | A created record cannot be corrected, reopened, or closed through the application. A mistake after creation needs a reset or an out-of-band correction, so the record is not a full case lifecycle. | Treat records as immutable. Any update or close work is blocked behind Gate U in `docs/ROADMAP.md`, which requires a separately agreed contract before code or schema changes. An unsupported POST path is rejected with 404 and recorded as `unsupported_write_attempt`; other HTTP methods are not handled by the mock and are not audited. Update and close do not exist. |
| L2 | **No authentication or identity.** The mock has no login, session, role check, or signed reviewer identity. The operator CLI accepts a reviewer name as free text. | Any local caller can request a review, and the audit cannot prove who approved a draft. This is a training simulation, not a production human boundary. | Keep the service on loopback and use a separate operator terminal. Plan SSO, reviewer roles, and server-side authorization as the first mid-term item after Gate U. Do not expose the mock to a network. |
| L3 | **Loopback-only local mock.** `tools/runtime.py` binds `127.0.0.1` by default and stores state in a local SQLite file. | There is no shared environment, horizontal scaling, high availability, or team concurrency. Two people cannot safely use one state file at the same time. | Use one isolated copy and one state database per team, as `README.md` says. The dev container is for development only. A managed deployment is a later roadmap item. |
| L4 | **No batch processing.** The API has no batch endpoint, and the runner processes cases one at a time. | Bulk intake, queueing, rate limiting, and partial-batch recovery are not available. Throughput is bounded by one process and one case at a time. | The runner isolates a failed case and continues with the rest, so one bad case does not stop the array. Bounded retry is near-term roadmap item N3. Batch intake and a queue are mid-term roadmap items, after auth. |
| L5 | **Deterministic template narrative, no model fluency.** `src/contract.py` `_narrative` returns a fixed template sentence, plus a second sentence naming outstanding fields when evidence is missing. #54 adds a four-section draft in `src/narrative.py` behind an optional `ProseWriter` seam; the seam is unwired and no model client exists. | The draft is terse and not tailored to the customer. It does not produce a fluent customer message, and it cannot adapt tone or length. | The deterministic fields are complete and auditable, and the template is always available as a fallback. A model narrative route is optional, gated on client approval, and limited to prose by `docs/decisions/ADR-001-model-narrative-boundary.md`; #54 does not record a model id, prompt version, or validation result, so step 7 of the ADR stays open. `ADR-003` adds two closed model questions on the classification gap; it does not change the narrative. |
| L6 | **No UI.** There is no web front end, reviewer dashboard, or case list screen. Output is JSON and command-line text. | A reviewer must read JSON or use the operator CLI. There is no visual diff, no click-to-approve, and no case workspace. | Use the documented CLI flow and the audit export. An analyst UI is a later roadmap item. No UI capability is claimed in the demo. |
| L7 | **No OCR or document parsing.** Evidence is read as Markdown text by source id; #52 pins the read to UTF-8 (fixtures are ASCII). | Scanned images, PDFs, email files, and arbitrary attachments are unsupported. A case that names a document the runner cannot read stops rather than guessing. | The supplied attachments already contain readable text, which is why OCR is out of scope. The runner refuses unread sources and reports the reason. Any OCR or parser work requires a new scope decision. |
| L8 | **Synthetic 2026 data only.** All institutions, people, policies, records, and currency are fictional. Scenario dates are fixed in 2026. | Results do not estimate production accuracy, fraud rates, customer behaviour, or real policy coverage. There is no real customer data, real money, or production traffic. | Keep fixtures fixed and versioned. Never substitute today's date for a scenario date. Use hidden assessment cases for coverage, not as a statistical sample. Make no accuracy or cost claim that was not measured. |
| L9 | **Partial classification coverage.** `src/contract.py` `_classification` uses deterministic phrase matching over the intake fields and customer statement, not a semantic classifier. | `unauthorized` (denied, or absent authorization without a denial), `duplicate_charge` (charging verb with two-charge wording) and `service_not_received` (confirmed authorization with an undelivered service) are assembled, including missing-evidence drafts. Conflicting accounts and cash withdrawals are escalated to `ambiguous` or `unsupported` before classification (PR #52, which carries #53's work); unseen wording for a supported type can still fail closed. | Roadmap items N1 and N2 track what PR #52 leaves open. Fail closed on anything the rules cannot establish: never guess a type or a deadline. With a qualified model configured (`ADR-003`, off by default), wording the rules miss is typed from the customer line the model names, with that line cited and a reviewer note, or sent to a person; without one the case still fails closed. |
| L10 | **Approval and creation are not wired into the runner.** `src/api_models.py` models review and record bodies, and the mock enforces draft hashes and idempotency, but the contract runner does not call `POST /v1/reviews` or `POST /v1/records`. | The application path from draft to approved record is incomplete. A human can use the mock and operator CLI, but the application does not yet submit the draft or create the case itself. | Wire the two calls as near-term roadmap item N4. Preserve the draft hash, the `Idempotency-Key`, and the duplicate `409` handling. Never create a record manually to cover the gap. |
| L11 | **No retry budget for tool faults.** Each tool read is attempted once on this branch. A 503 stops that case. | A transient failure such as the supplied `CARD-D10` fault is not recovered, and a persistent failure is not distinguished from a transient one by the runner. The procedure allows three total attempts before escalation. | The runner continues with other cases and reports the reason for the stopped case. PR #56 (COF-40) adds bounded retry with backoff and a circuit breaker in `src/resilience.py`, but nothing calls it yet, so D10 still stops. Wiring it into the read path and routing persistent failures to `manual_review` remain roadmap item N3. Never treat a failed read as an empty transaction history. |
| L12 | **Fixed citation set and substring evaluation.** Assembly emits six citations for a normal case from the intake, attachment, transaction body, procedure, and policy; PR #52's escalated and duplicate paths add or replace slices (a second charge row, a source-id line, a duplicate-deadline line). The evaluator checks that a quote is an exact substring, not that it semantically supports the claim. | Evidence outside those six slices is not cited. An exact quote can still be a poor justification, so automated passing does not prove grounding. | Claim names keep each citation checkable, and a human reviewer checks semantic support. ADR-002 keeps the policy and deadline citation tied to one version. Richer evaluation, including semantic citation review, is a roadmap item. |
| L13 | **Audit and state are local SQLite.** The audit table is an append-only sequence in a mutable local file. There is no write-once store, remote shipping, or independent retention. | The audit is useful for a demo and for debugging, but it is not tamper-evident and does not survive loss of the local file. It is not an immutable compliance record. | Export the audit to JSON for review, as the README shows. A managed, append-only audit store is a later production item. Do not describe the local table as immutable. |
| L14 | **No production deployment or observability.** The repository ships a dev container and a local `serve` command. There is no production image, orchestration, metrics endpoint, tracing, alerting, or log pipeline. | Operation is manual. Health is the mock's `/health` only. There is no capacity, latency, or error dashboard. | Use the runbook commands and local state for the assessment. `tools/scored_run.py` measures per-case template latency and records zero model calls and zero tokens (cost 0.00 by construction, not a price estimate) in `reports/scored-run.md`; a model route still needs its own measured latency and cost. `tools/hybrid_eval.py` reports the hybrid's model calls and tokens per suite in `evals/reports/hybrid-eval.json`; on recorded answers the latency is the recorded one, not a fresh measurement. Containerisation, managed state, redacted structured logs, and monitoring are later roadmap items. |
| L15 | **Single currency and simulated external systems.** All supplied amounts use `XCR`. Payment, merchant, and customer systems are fixtures, not external APIs. | There is no currency conversion, multi-currency formatting, or real network integration. A production adapter would need new validation and failure handling. | State the single-currency scope in the demo. Keep the mock boundary explicit. External integrations and multi-currency are later items only if the client asks for them. |
| L16 | **Model-assisted classification is qualified on synthetic text and not yet approved.** `ADR-003` lets a qualified model answer two closed questions. GPT-6 Luna passed 66 synthetic qualification cases and 11 of 12 held-out cases (one network failure), on the copilot's client; `approved_by` is empty. | A live answer can be wrong, and 78 synthetic cases are not a statistical estimate of production accuracy. A live run sends the customer's redacted lines to the provider, and depends on it: no answer leaves the rules to decide. | Off by default. A live pair runs only with a passed record in `models.toml` for the current schema hash (zero unsafe answers, at least 90% answered) and a recorded approval, so live use is refused today. No model is asked about a statement holding text the detectors recognise as an instruction or as addressed to a model, or a restricted value redaction would miss; unrecognised phrasing still reaches it. Every model-assisted draft tells the reviewer which line to verify, and every call is metered. CI and evaluation replay recorded answers. The records came from the copilot's client; rerun `tools/qualify_model.py` with this repository's client before the bank signs off. |

## Limits that are not defects

Some boundaries are deliberate and should not be presented as incomplete work:

- No adjudication and no promise of refund, reimbursement, success, or eligibility.
- No instruction from a merchant note or attachment is followed.
- No case is created before a human approves the exact draft.
- No policy, transaction, merchant, or citation is invented when the supplied source is missing.

## How to use this list in the demo

Name the limitation, the impact, and the mitigation. Do not claim a target-state capability as if it ships. The roadmap in `docs/ROADMAP.md` maps each material limitation to a near, mid, or later item, and Gate U blocks the largest scope change until a separate contract is agreed.
